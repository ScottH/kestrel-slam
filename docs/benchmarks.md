# Benchmarks

Only **measured** numbers go here, each with the commit, configuration and command that produced
it, so anyone can reproduce them with Docker. Comparisons with other systems will be added from
their papers' tables, with citations, never from memory.

## How to reproduce

```bash
export KESTREL_DATA_DIR=~/code/kestrel_slam/data   # datasets under $KESTREL_DATA_DIR/datasets
docker compose run --rm build
docker compose run --rm shell /ws/src/kestrel_slam/tools/regression_report.py   # all registered sequences
```

TUM-VI "euroc" exports (512×512, 16-bit) are available from
`https://cdn2.vision.in.tum.de/tumvi/exported/euroc/512_16/dataset-room<N>_512_16.tar`
(≈ 1.7 GB each, ~5 MB/s). Extract to `$KESTREL_DATA_DIR/datasets/tumvi/room<N>_512_16/`.

## Regression testing

One script produces the summary table for every registered dataset, the same way every time,
and compares it with the accepted baseline:

```bash
export KESTREL_DATA_DIR=~/code/kestrel_slam/data
docker compose run --rm build
docker compose run --rm shell /ws/src/kestrel_slam/tools/regression_report.py
```

* **Registry:** `tools/benchmarks.yaml` lists the sequences (dataset folder, config, group) and
  the regression tolerances. **To add a dataset**, add one line there. Sequences whose data is
  missing on a machine are skipped and listed as such.
* **Report:** each run writes `$KESTREL_DATA_DIR/results/regression/reports/<date>_<commit>/`
  with `report.md` (summary table with mean/median/max rows plus the regression check),
  `summary.json` (all numbers, commit, machine) and per-sequence results (trajectories,
  `loops.txt`, plots). `results/regression/latest.md` is always the newest report.
* **Baseline:** `tools/regression_baseline.json` (committed) holds the accepted numbers. A
  sequence **regresses** if ATE (VIO or final SLAM) grows by more than 15 % (or 5 mm, whichever
  is larger) or if it gains resets or wrong loops. The script then exits with code 1, so it can
  gate merges. After an intentional change, accept the new numbers with `--update-baseline` and
  commit the baseline together with the change that caused it.
* Options: `--sequences A B` (subset), `--skip-run` (re-score existing results), `--no-fail`,
  `--starts 0 4 8` (see below).
* **Single runs are a regression guard; decisions need averaged runs.** Odometry drift over a
  long sequence is chaotic: a harmless change can move one sequence's VIO ATE by ±50 %, while the
  mean over all sequences barely moves. The baseline (single run, start frame 0) catches gross
  regressions. To judge whether an algorithm change is *better*, run `--starts 0 4 8` for the
  old and the new version and compare the averages, as was done for M4 (theory ch. 07 §3.2).

### Quick regression test in CI

Every push runs `regression_report.py --ci` after the unit tests. It uses the first 40 s of TUM-VI
room1 (800 stereo frames, about 20 loop closures). On a GitHub runner the step takes about 60 s, and the numbers match the laptop baseline to the millimetre.

* **Data:** clip + vocabulary in one archive, the release asset
  [`ci-data-v1`](https://github.com/ScottH/kestrel-slam/releases/tag/ci-data-v1). CI checks its
  SHA-256 (pinned in `.github/workflows/ci.yml`) and caches it. To run it locally:
  ```bash
  curl -fL -o kestrel_ci_data.tar.gz \
    https://github.com/ScottH/kestrel-slam/releases/download/ci-data-v1/kestrel_ci_data.tar.gz
  tar -xzf kestrel_ci_data.tar.gz -C $KESTREL_DATA_DIR      # datasets/ci/... + vocabulary/
  docker compose run --rm shell /ws/src/kestrel_slam/tools/regression_report.py --ci
  ```
* **Checks:** each sequence passes or fails on its own, against `tools/regression_baseline_ci.json`
  and the `ci_tolerances` (ATE +25 % or +1 cm; no new wrong loops or resets; at least half the loop
  closures). The clip runs **twice**, and the trajectories and loops must be byte-identical. Timing
  is reported but not checked. The report is attached to the CI run as the `regression-report`
  artifact.
* **Changing the clip:** run `tools/make_ci_clip.py` (deterministic archive), publish it as a new
  release (`ci-data-v2`), update `CI_DATA_URL` / `CI_DATA_SHA256` in `ci.yml` and
  `ci_sequences`, then run `regression_report.py --ci --update-baseline`.
* **An intentional change in results** (better or worse) needs `--ci --update-baseline`
  committed in the same PR, just like the full baseline.

Timing columns are machine-dependent (the report records CPU and core count). Compare timings only
between reports from the same machine.

Metrics (`tools/evaluate.py`, evo):

* **ATE RMSE**: absolute trajectory error after SE(3) Umeyama alignment (no scale: stereo knows
  metric scale).
* **RPE 1 m**: relative translation error over 1 m segments (drift per metre).

\* room5 ran while another dataset was being extracted, so its timing is inflated.

Notes

* All six sequences run to completion with zero resets. Drift per metre is consistent
  (1.6–2.1 cm).
* room2's larger ATE is accumulated drift in its inner loops (peak 34 cm). The estimate keeps the
  correct shape throughout. Loop closure (M5) is what removes this kind of error.
* TUM-VI cameras run at 20 Hz, so 28 ms/frame is real-time with margin. The keyframe solve is
  the largest cost (median ≈ 28 ms) and is the first target for M10 performance work.
